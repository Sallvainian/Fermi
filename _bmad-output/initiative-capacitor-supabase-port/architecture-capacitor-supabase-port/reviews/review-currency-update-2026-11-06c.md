# Review: Currency of the .github Ownership Move to epic-platform-baseline

- **Artifact:** `architecture-capacitor-supabase-port.md`, uncommitted diff to the Structural Seed (lines 358-362, `.github/` block); `epic-map-capacitor-supabase-port.md`, uncommitted diff to rows 1 and 13; read alongside the sources they adopt: `tickets/epic-platform-baseline/epic-platform-baseline.md` (R10-R13, Notes dated 2026-11-06) and `tickets/epic-platform-baseline/tickets/tickets.toml` stories 1, 12, 3 and 13
- **Lens:** was each committed decision web-researched or reality-checked, or asserted from training data? Does each named technology still exist and fit?
- **Reviewed:** 2026-11-06
- **Verdict:** The ownership move itself holds. Every file, workflow and secret it names exists today as stated, the "ten secrets only they use" count is exact, and both actions it leans on are at their current majors. One plan assertion fails a reality check: making `test.yml`'s summary job a required check "on the Main ruleset". Fermi's Main ruleset targets every branch (`~ALL`), while My-Love's targets only the default branch. GitHub's rule definition says a required check means "commits must first be pushed to another ref where the checks pass". On `~ALL` there is no other ref, so the plan's own model (Dependabot branches, auto-merge) would conflict with it. Two smaller gaps follow from reading My-Love's and Fermi's live behaviour: an auto-merged Dependabot pull request does not trigger `deploy.yml`, and repo-level Dependabot security updates run outside `dependabot.yml`.

## Findings

### F1: HIGH. Adding the required check to Main as Main stands would gate every branch, not just main

- **Where:** epic map row 1, "`test.yml`'s summary job as the Main ruleset's required check". Adopted from R12, story 13 ("adds story 3's test.yml summary job as a required status check on the Main ruleset") and the epic's line 17 ("the Main ruleset requires test.yml's summary check before a merge").
- **Evidence:** Fermi's Main ruleset has `conditions.ref_name.include: ["~ALL"]`, as did its prior version. My-Love's Main, which story 13 names as the model, has `["~DEFAULT_BRANCH"]`. GitHub's rule definition says a required check means "commits must first be pushed to another ref where the checks pass". `do_not_enforce_on_create` lets a branch be created, but it does not cover later pushes to that branch. The only bypass actor is the admin role. Dependabot, `github-actions[bot]` and the Claude app are not in it. Fermi's `~ALL` ruleset also carries `non_fast_forward`. Under My-Love's strict policy, Dependabot must rebase its branch, and that rebase is a force push.
- **Impact:** Story 13 asserts that a Dependabot pull request "merges itself once it is green". With the check on `~ALL`, Dependabot's pushes to `dependabot/*` branches (and the Claude app's pushes to its branches) face the required check, and, with strict mode, Dependabot's rebases also face `non_fast_forward`. This conflicts with that assertion. The plan was checked against My-Love's ruleset, not Fermi's. UNVERIFIED by a live test: whether today's `~ALL` `pull_request` rule already blocks bot pushes. The only Dependabot pull request, #84, was opened on 2025-11-18, and no later bot push shows either way. Story 13's verify step would catch the failure, but only after the ruleset is changed.
- **Fix:** Have story 13 say outright that Main's target changes to `~DEFAULT_BRANCH`, as on My-Love, in the same owner-approved ruleset edit that adds `required_status_checks`. Then decide whether the `pull_request` rule stays, since My-Love has none. Alternatively, add the check in a second ruleset scoped to `~DEFAULT_BRANCH` and leave Main alone. The spine needs no change. The epic map row could read "the Main ruleset, targeted at the default branch, requiring `test.yml`'s summary job".

### F2: MEDIUM. A self-merged Dependabot pull request does not deploy

- **Where:** epic map row 1, `dependabot-auto-merge.yml` beside `deploy.yml`; R12 "a Dependabot pull request merges itself once the required check passes"; story 1's deploy.yml "on a push to main".
- **Evidence:** My-Love's auto-merge enables `--auto` with `GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}`, so GitHub performs the merge as `app/github-actions`. GitHub's docs say events from `GITHUB_TOKEN` "will not create a new workflow run". My-Love's live history agrees. PRs 440 and 441 (merged 2026-11-02 by `app/github-actions`) have no `push` run of Tests or Deploy on their merge commits.
- **Impact:** In Fermi, `deploy.yml` on a push to main is the only path for migrations, Worker deploys and the live update (AD-18). A merged Dependabot bump sits on main undeployed and untested on main until the next human push. During that window, the site's commit-id check reports a build older than main's HEAD. This is harmless to correctness, because the pull request's own `test.yml` run gated it, but nothing in the plan says it happens.
- **Fix:** Pick one and record it in story 13's Notes. (a) Accept it: the next human push deploys the bump, as on My-Love today. (b) Run the merge with a GitHub App token, so the push event fires. (c) Give `deploy.yml` a `workflow_dispatch` trigger and have the auto-merge job dispatch it after merging. Choosing (b) or (c) needs a reality check of its own before story 13 builds it.

### F3: MEDIUM. Repo-level Dependabot security updates run outside `dependabot.yml`, so R11's "nothing else, without errors" is not what story 1 delivers

- **Where:** R11 ("for GitHub Actions, and for nothing else, and its jobs run without errors"); the spine seed comment "`dependabot.yml  # app/ npm and GitHub Actions only`".
- **Evidence:** Dependabot security updates are enabled on the repo. Run 42108401894 (2026-11-05) was a `security` job over `["/.","/functions"]`, although `dependabot.yml`'s npm entry names only `/`. It failed on `functions/`'s `mcp-firestore` path dependency. Story 1 deletes the root `package.json`, which removes `/.`. `functions/` stays until epic-app-store-release.
- **Impact:** Story 1's verify ("Dependabot shows its /app npm and github-actions jobs with no errors") can pass while security-update jobs on `functions/` keep failing, so R11 as worded is not met. After story 13, any security pull request Dependabot does manage to open for `functions/` would merge itself. `test.yml`'s change detection would class it as non-app, and the summary would pass. That is low harm, given the Firebase app has no live users.
- **Fix:** Narrow R11 and the seed comment to version updates, and record in epic-platform-baseline's Notes that security-update jobs on `functions/` may fail until epic-app-store-release removes that folder. If R11 must hold literally, story 1 needs a researched way to keep security updates off `functions/`. `dependabot.yml`'s `exclude-paths` exists, since the job definition carries `"exclude-paths":[]`, but whether it applies to security updates is UNVERIFIED.

### F4: LOW. The seed comment assigns `apple-secret.yml` to epic-platform-baseline

- **Where:** spine line 360-362: `workflows/  # deploy.yml, test.yml, keep-alive.yml, apple-secret.yml, backup.yml, dependency-review.yml, dependabot-auto-merge.yml, claude.yml, claude-code-review.yml (all epic-platform-baseline)`.
- **Evidence:** Epic map row 2 owns `apple-secret.yml`. The parenthesis closes the whole list.
- **Impact:** A reader of the seed alone could build `apple-secret.yml` in epic 1. That is the drift the memlog says this amendment prevents.
- **Fix:** Use "(all epic-platform-baseline except apple-secret.yml, epic 2)", or drop the ownership note and leave ownership to the epic map.

### F5: LOW. The required check's name and source are not pinned

- **Where:** story 13, "adds story 3's test.yml summary job as a required status check"; story 3, "one summary job ... as My-Love's Test Summary".
- **Evidence:** A ruleset matches a workflow check by `<job name>`, ignoring workflow and trigger. My-Love's context is `Test Summary` with no `integration_id`, so it accepts the status from any source.
- **Impact:** If story 3 names the job differently, the ruleset waits forever on a check that never reports. Without `integration_id`, any integration with status-write access can satisfy the check.
- **Fix:** Have story 3 fix the job's `name:` (for example `Test Summary`) and story 13 require that exact context, optionally with GitHub Actions as the source.

## Not findings

- `dependabot/fetch-metadata` (current v3.1.0) is not part of this change. My-Love's auto-merge does not use it, and nothing in the diff or stories names it. If story 13 later gates majors on update type, the current major is v3.
- Allow auto-merge is off on Fermi (`allow_auto_merge: false`). Story 13 already lists turning it on as hitl setup, which matches GitHub's docs.
- `actions/dependency-review-action@v5` is the current major, and `fail-on-severity: moderate` is a valid value. Neither is out of date.
